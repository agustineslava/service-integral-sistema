MIGRACIONES DE EMPRESA (tenant)
===============================

Acá van los cambios de esquema que se aplican a la base de CADA empresa.

Reglas:

  1. Un archivo por cambio, numerado:  001_algo.sql, 002_otra_cosa.sql
     El número define el orden. Nunca se reutiliza un número.

  2. Un archivo ya aplicado NUNCA se edita. Si algo salió mal, se crea una
     migración nueva que lo corrija. El motor detecta si un archivo cambió
     y aborta: eso evita que dos empresas terminen con esquemas distintos.

  3. EXPAND-CONTRACT. Mientras se despliega, el código viejo y el nuevo
     conviven unos minutos. Entonces:
        BIEN:  agregar columna NULL o con DEFAULT
        BIEN:  crear una tabla nueva
        BIEN:  agregar un índice
        MAL:   renombrar una columna en un solo paso
        MAL:   borrar una columna que el código todavía usa
     Para renombrar o borrar: se agrega lo nuevo en una migración, se
     despliega, se deja de usar lo viejo, y RECIÉN DESPUÉS una migración
     posterior lo elimina.

  4. Las migraciones no llevan USE, ni CREATE DATABASE, ni DROP DATABASE.
     El motor ya está conectado a la base correcta.

  5. TODA MIGRACIÓN TIENE QUE SER REAPLICABLE.
     Corrida sobre un esquema que ya la tiene, no cambia nada.

     La base de una empresa nueva se arma en dos pasos, en este orden:

        1. se carga `schema/base.sql`
        2. DESPUÉS se corre esta cadena de migraciones encima

     `base.sql` es una CONGELACIÓN: el esquema antes de que existiera la
     primera migración. No trae presupuestos, ni etiquetas, ni facturas, ni
     la columna `precio_cobrado`. Así que la cadena se corre sobre un esquema
     que todavía NO la tiene, que es la forma normal.

     Igual la regla sigue, por dos razones.

     La primera es que este proyecto no solo da de alta empresas: también
     ARMA BASES NUEVAS para probar cosas. Si hay que reconstruir la base de
     una empresa, se hace con `base.sql` más esta cadena, y ahí sí importa
     que la 006 se pueda correr dos veces.

     La segunda es que una migración reaplicable cuesta un `IF`, y una que no
     lo es rompe el alta sin decir por qué. Cuando las dos dan el mismo
     resultado, se elige la que se rompe antes y más fuerte.

     En la práctica:

        BIEN:  CREATE TABLE IF NOT EXISTS ...
        BIEN:  un ALTER guardado con un IF sobre information_schema, armado
               con SQL dinámico (MySQL no tiene ADD COLUMN IF NOT EXISTS;
               MariaDB sí)
        MAL:   ALTER TABLE ... ADD COLUMN a secas
        MAL:   DROP COLUMN a secas
        MAL:   cualquier cosa que dé por hecho que el esquema está "virgen"

  6. UNA MIGRACIÓN NO TOCA `schema/base.sql`.

     `base.sql` es la congelación de antes de la 001. Si una migración nueva
     necesita una tabla, esa tabla la crea la migración. Meter la tabla en
     `base.sql` es volver al problema de antes: el taller la tiene y las
     empresas nuevas no, sin que nada lo note.

Cómo se aplican:

    npm run migrate -- --tenant ServiceIntegralsistema --dry-run
    npm run migrate -- --tenant ServiceIntegralsistema

  A toda la flota de una vez:

    npm run migrate -- --fleet --dry-run
    npm run migrate -- --fleet

Este directorio tiene los cambios de esquema que se aplican a la base de CADA
empresa: 004 presupuestos, 005 etiquetas QR, 006 facturación interna.

Antes de la 004, el esquema base venía de `schema/schema-actual.sql`, que era
también lo que se cargaba al dar de alta una empresa. Ahí está el bug que
costó una:

    `altas.js` cargaba el volcado del esquema FINAL y después corría la cadena
    encima. El volcado ya traía las tablas, así que las migraciones veían
    `CREATE TABLE IF NOT EXISTS`, se las salteaban, y quedaban como aplicadas
    sin haber hecho nada. Para el taller, que ya tenía todo, no se notaba.

    Para una empresa nueva, la 006 moría en el paso 2 con
    `Duplicate column name 'precio_cobrado'`, y toda alta quedaba rechazada.

Y las verificaciones daban verde, por dos motivos:

    - `f4:verificar` armaba su base de empresa con el MISMO volcado. Probaba
      el camino roto, así que pasaba.
    - el motor tiene un ledger. Contra una base ya migrada nunca intenta
      correr la 006, y nunca ve el problema.

Por eso ahora hay tres cosas distintas, y las tres importan:

    `schema/base.sql`
        La congelación. La carga el alta. No se le tocan las tablas.

    `schema/schema-actual.sql`
        Un volcado del estado final, SOLO para leer. Los verificadores sacan
        de ahí la lista de columnas con la que comparan el código. Si algún
        día queda viejo, esos verificadores comparan contra la nada; por eso
        hay que regenerarlo con `npm run schema:snapshot` cuando cambia el
        esquema. NO se usa para armar bases.

    `npm run ver:base`
        Arma una base de verdad con `base.sql` más esta cadena, la compara
        con el taller tabla por tabla, columna por columna, tipo por tipo,
        y la borra. Dice si la congelación está bien.

    `npm run f4:verificar`
        Da de alta una empresa de verdad, con el mismo camino que el alta, y
        usa la base.

Los dos últimos existieron porque el primero no.
